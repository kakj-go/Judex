### Q001 — 自动触发的角色 AI 在哪里运行？

**问题**：主管提交内容后，即使项目经理电脑关机，是否也要求项目经理角色 AI 自动分析？你设想的平台 AI 是平台运行的项目角色，还是必须调用该成员电脑上的个人 AI 工具？

**可选方向**：

- A：平台运行协同分析 AI，本地工具执行本地工作并接入提交。
- B：平台通过成员电脑上的常驻执行端派发任务，离线时排队或改派。
- C：平台只创建待办，成员主动用本地 AI 领取和处理。

➡️ **建议 A**。平台负责分析、评审、拆解等协同工作，本地 AI 负责代码和本地操作。Skill 负责协议接入；若要 B，还需要明确开发常驻执行端，不能只靠一份 Skill 保证自动唤醒。

**答案影响**：平台 AI 基础设施、本地软件安装方式、离线体验、模型费用、工具兼容范围。

**用户答复**：“在项目平台执行”。  
**确认结果**：自动角色 AI 在项目平台运行，本地软件通过 Skill 接入；不以成员电脑在线作为平台分析的前提。  
**状态**：根决定已确认；接入与模型配置进入 Q007、Q008。

### Q002 — 角色是项目公共岗位，还是绑定成员的工作身份？

**问题**：项目里有两名开发、两名测试时，是每个人都有自己的角色 AI，还是共享一个“开发 AI”和一个“测试 AI”？一人能否同时担任主管和项目经理？每次交接最终由谁负责？

➡️ **建议“角色模板 + 成员的项目角色实例”**。可以一人多岗、同岗多人；每次交接指定一个负责实例。AI 以该工作身份生成建议，真人责任与工具权限分别记录。

**答案影响**：任务分配、个人待办、提示词定制、代理决策、角色缺岗和多方审批。

**用户答复**：“项目可以设定这个AI的角色提示词，然后每个人加入为这个角色之后可以设定自己的提示词”。  
**确认结果**：项目角色提示词与成员加入该角色后的个人提示词分开配置；个人配置不是修改全项目公共角色。  
**首轮未确认，后续更新**：第二轮 Q009 已确认兼岗和同岗多人、AI 选择多人；Q022 已确认项目职责优先。集合变化与提示词版本进入第三轮。  
**状态**：两层提示词已确认；人员分配与合成规则进入 Q009、Q022。

### Q003 — 人类逐份提交报告，还是只控制关键决策？

**问题**：你多次提到项目经理、主管、测试本人决定是否提交。是否要求每个角色每轮报告都必须本人查看并提交后，下一位 AI 才能开始？还是允许 AI 在限定议题内先交换分析，最终把分歧和结论交给人类？

➡️ **建议关键关口决策**。允许 AI 自动形成草稿和有界讨论；需求与架构基线、范围变化、交付验收、生产发布等正式决定由责任人处理。报告可见范围与具体关口下一轮细化。

**取舍**：逐份提交更贴近你的原始示例，但人的待处理数量随 AI 讨论轮数增加；关口决策更省人力，却需要清楚区分草稿、提议和正式表态。

**答案影响**：自动讨论机制、待审批队列、报告发布规则、事件触发和责任追踪。

**用户答复摘录**：“AI 内部可以讨论决策”“结论要对应的角色同意发送这段讨论给同意人”“项目经理作为接收方其同意之后才认为讨论结束”。人类还可补充内容，让 AI 继续讨论；接收方也可先让 AI 分析，再决定同意或不同意。  
**确认结果**：AI 内部讨论 → 相应角色真人确认发送结论 → 指定接收方 AI 可辅助分析 → 接收方真人接受才完成交接；未接受可以补材料、继续讨论并重新提交。  
**修正首轮建议**：不能只写笼统的“关键关口”。正式发送与接收认可是两个不同真人动作，主管不固定为最终同意人。  
**状态**：主线已确认；参与者、讨论运行和生效动作进入 Q009、Q011、Q013；异常动作在 Q010 后续细化。

### Q004 — 正式成果以网页正文为准，还是结构化记录附带网页？

**问题**：如果网页写着“这次完成三个任务”，平台是只保存网页，再让 AI 临时理解，还是同时保存明确的任务 ID、版本、验收项和待决定事项？网页和文档应该只是展示附件，还是项目状态的主要依据？

➡️ **建议结构化记录附带有版本的阅读内容**。允许 AI 从内容提取候选字段，但经校验和相应确认后才改变正式业务状态。这样原始网页可自由表达，任务和审批仍能可靠运行。

**答案影响**：数据模型、Skill 协议、页面预览、搜索、版本与证据追踪。

**用户答复归纳**：AI 使用代码、项目协同任务，以及上传图片、网页、文档、文字、代码等项目文件内容，可以自行分析成果；上传内容与产物需要结构化存储。  
**确认结果**：项目内容参与 AI 分析，上传内容和 AI 产物结构化保存。  
**未确认**：具体字段、版本规则、网页运行能力；不把上传文件仅当作不参与分析的展示附件。  
**状态**：内容范围和结构化存储已确认；网页能力与产物生效方式进入 Q012、Q013。

### Q005 — Judex 是协同中枢，还是必须经过的执行关口？

**问题**：如果成员直接在 Git 合并、直接用自己的工具部署，Judex 应记录和提示这些变化，还是必须从权限层面阻止未经过 Judex 的动作？这决定“代码仓库管理”需要多深。

➡️ **建议首版以协同和核验为主**，明确显示人工上报、外部核验和流程偏差；如果你要求它成为组织的强制交付入口，就从首版设计 Git 保护规则与部署权限的实际约束。

**取舍**：只有平台审批记录无法阻止外部管理员绕过；真正约束外部操作需要 Git 和部署系统共同配合。

**答案影响**：Git 权限、分支保护、审批映射、外部事件对账、部署集成深度。

**用户答复**：“对 git 没有约束，只是可以自行做一些代码分析和修改提交”。  
**首轮确认结果**：不强制约束外部 Git，保留分析、修改和提交能力。  
**第二轮细化**：Q014 增加阶段分支来源与纳管资格，平台管理的合并须相应人员审批；外部可自行操作，但非阶段来源不纳入交付识别监控。此处以该较新边界为准。  
**未确认**：平台代码写操作能自动进行到哪一步、用什么身份、允许写哪些分支；部署控制边界不由这条 Git 答复代替。  
**状态**：Git 管理定位已确认；平台自身写行为进入 Q014，提供商与授权细节后置到 Q024。

### Q006 — 第一批要验证的真实使用场景是什么？

**问题**：优先验证一个人带多个角色 AI、一个真实团队各自使用本地 AI 协作，还是从第一版就服务多个彼此独立的客户组织？这三者的主要阻力分别是自动编排、多人交接和组织隔离运营。

➡️ **建议先验证一个真实团队的交付闭环，并支持一人兼任多个角色**。组织与项目的资源归属从模型上留清楚，商业化租户运营范围等体验验证后再确定。

**答案影响**：身份与邀请、资源归属、权限模型、部署方式、首版范围和成功指标。

**用户答复**：“一个团队各自使用本地 AI 协作”。  
**确认结果**：首批场景为真实团队的本地 AI 协作。  
**后续更新**：第二轮 Q009 确认兼岗，Q019 确认成员可建项目和负责人邀请管理；多客户商业化仍未提出。

### Q007 — 本地接入是否可以安装 Judex 工具？

**前提**：Q001 已确认平台运行角色 AI，本地使用 Skill 接入。

**问题**：为了让各种本地 AI 软件登录项目、上传文件包、读取任务和关联 Git，你是否接受成员安装一个 Judex CLI，再由 Skill 指导 AI 调用？还是要求只有 Skill，通过 HTTP 接口操作，不安装额外工具？

**用户答复**：Skill + CLI，并保留统一 API。  
**确认结果**：确定三层接入形式；后续细化登录、上传、恢复和支持矩阵。  
**状态**：已确认。

### Q009 — 同岗多人和讨论接收人如何确定？

**前提**：Q002、Q003 已确认成员角色、个人提示词及接收方决定结束。

**问题**：是否允许一人兼任多个角色、同一角色有多人？例如有两位项目经理，一次讨论应该自动发给整个岗位，还是明确选一位接收人？

➡️ **建议支持一人多岗、同岗多人，每次交接明确一个发送责任人和一个最终接收人**，其他人可以作为参与者。AI 可推荐接收人，正式提交前显示目标；联合同意和代理规则随后按需要细化。

**用户答复归纳**：支持兼岗与同岗多人，让 AI 自行决定交给哪些人，多个 AI 同时讨论；中间层讨论审批一个人同意即可往下执行，结论层须接收的人都同意才能完成。  
**确认结果**：AI 选择多人接收集合；中间层 ANY 同意可推进，结论层 ALL 同意才完成。真人发送确认仍遵守 Q003。  
**修正原建议**：不采用单一最终接收人，也不把 AI 限定为仅推荐路由。  
**状态**：主规则已确认；层级界定进入 Q010，集合与版本进入 Q025，异议失联后续进入 Q032。

### Q011 — AI 一轮讨论何时停止，讨论过程给谁看？

**前提**：Q001、Q003 已确认平台内部讨论和真人确认边界。

**问题**：AI 是持续往返直到有人介入，还是每轮达到结论、缺资料或运行上限就暂停等人？议题参与者是否能看到 AI 的讨论发言，还是只能看到最后报告？

➡️ **建议按轮次运行**：出现可提交结论、明确分歧或缺少资料，或达到轮次/预算上限时暂停；人类补充材料后继续下一轮。参与者可查看 AI 讨论发言和摘要，正式报告单独标识，个人未提交材料的可见性后续细化。

这里的讨论发言是平台保存的可见消息和成果，不要求获取或展示模型隐藏推理。

**用户答复**：按轮次运行，参与者可看发言与摘要；形成结论、缺资料或达到运行上限暂停，补材料后继续；正式报告与内部讨论分别标识。  
**确认结果**：采纳上述运行与展示规则。  
**状态**：已确认，运行预算细化进入 Q020。

### Q013 — 接收人接受结论后，任务和计划是否直接生效？

**前提**：Q003、Q004 已确认接收认可与成果结构化保存。

**问题**：报告提出三个阶段、十个任务，接收人点击接受后，平台是否直接创建或修改这些计划和任务，还是只结束讨论并保存报告，之后还要另行操作？

➡️ **建议报告附带 AI 生成的具体变更清单，接收人接受后自动应用列明的计划和任务变更**。用户无需再手工抄写；正文里没有列入变更清单的建议不自动执行。建仓、推送、部署等外部动作按各自确定的规则处理，不由一次阅读确认无限扩大授权。

**用户答复**：报告附具体变更清单，接受后自动创建或修改列明的计划和任务；人类确认时看到变更，无需手工转录。

➡️ **建议测试或项目经理确认计划测试完成时，将通过验收的开发任务统一转为完成**，计划继续等待部署。Bug 仍必须由测试人员复测关闭，不能用批量完成动作跳过未关闭 Bug。

**用户答复归纳**：任务从开发完成到测试验收完成要由测试手动修改；界面创建 Bug 必须关联任务，任务进入修复中。全部 Bug 修复完成后，测试或经理可手工设任务已完成；计划全部任务已完成时，计划同步已完成。  
**确认结果**：采用任务人工验收→计划自动聚合完成，不再额外要求手动完成计划。文档统一用“已完成”表示任务的测试验收终态，开发完成只是待验收。  
**待对齐**：计划已完成与原测试完成/部署完成的显示关系进入 Q049；此前 Bug 复测关闭规则保留，不把任务完成当作自动关闭所有 Bug。  
**状态**：任务终态与聚合原则已确认。

### Q046 — 后续 Bug 的新计划是否保留旧 release 维护路径？

**问题**：原来发布后 Bug 从旧 release 切 bugfix，并同步更高 release/main；现在要求后续 Bug 进入新计划池走同套流程，而普通计划 feature 都从 main 创建。这里选择哪一种？

- A：Bug 纳入新的普通计划，从 main 建 feature，测试完成后形成新 release，按新版本修复。
- B：保留维护计划类型，共用计划状态机，但任务仍可从旧 release 切 bugfix 并传播到多个版本。

➡️ **若首版希望严格统一这套流程，建议 A**。如果仍需 B，必须明确维护计划的分支目标与“所有任务合计划 feature”的例外，不能同时把两条规则作为同一任务的唯一基线。此前旧版本维护能力在本题答复前不默默删除，也不宣称已经完成对齐。

**用户答复归纳**：某计划的 Bug 在对应计划中创建，走对应 release 修复；按 release 版本往前递进合并，合入哪些版本由用户选择，不由 AI 自动选择。  
**确认结果**：保留版本内维护和递进合并，不采用所有 Bug 自动创建新普通计划的方案。传播只作用于用户选定目标，不默认覆盖全部高版本或主分支。  
**待细化**：同 release 的维护修订和再次部署见 Q051，源任务是否等待所有选中目标见 Q052。  
**状态**：维护路径和目标选择权已明确。

### Q047 — 测试中出现开发工作，计划是否回退？

**问题**：计划已经测试中，新增一个本计划 Bug，或某任务被退回开发，计划整体应该回开发中，还是保持测试中而允许其下修复任务开发？

➡️ **建议只要本计划还有未开发完成的任务或修复工作，就自动回开发中；修复合入、全部再次开发完成后回测试中**。等待复测关闭的 Bug 不等于仍在编码，但会继续阻止计划测试完成。部署完成的历史计划不因此回退。

**用户答复**：计划回退到开发，本质是计划状态与任务、Bug、进度正相关。  
**确认结果**：计划需要随关联工作变化回退，不能将已交付计划永久锁定为不可回退。部署成功历史仍独立保留。  
**待对齐**：与 Q044 测试中回退的优先级在 Q050 明确。  
**状态**：工作驱动回退原则已确认。

### Q048 — 新计划池存待计划事项，还是每个 Bug 一个计划？

➡️ **建议池子保存待计划需求和 Bug，AI 可以归并相关事项形成未计划的计划草案，经审批后进入计划中，再分配任务**。保留每个原始事项与计划/任务的关联，不强制一条 Bug 对应一个完整计划。

**用户答复**：Bug 都是对应版本新建，不自动到新计划池。  
**确认结果**：撤回部署后 Bug 自动进入新计划池及事项归并建议；Bug 关联版本和任务，归属对应计划。正常新需求仍可另行创建计划，不因 Bug 自动创建计划。  
**状态**：Bug 归属已确认，新计划池分叉关闭。

### Q049 — 计划已完成和版本已部署是否分开显示？

**问题**：全部任务验收完成后，计划已完成，但版本可能尚未部署；已部署版本新建 Bug 后，计划又要进入修复工作。继续用“已完成→部署完成”的单一主状态，还是分别显示计划工作状态和部署状态？

➡️ **建议分开显示**：例如“计划已完成 · 待部署”“计划开发中 · 旧修订已部署”。工作状态随任务和 Bug 回退，部署历史保留；一次旧版本部署回报不能把新的修复工作覆盖成完成。若保留单主状态，需要明确其聚合优先级。

**用户答复**：可以分开。  
**确认结果**：计划工作状态与部署状态分开显示。工作随任务和 Bug 变化，旧部署事实保留，不由旧部署回报覆盖当前修复工作。  
**状态**：已确认。

### Q050 — 同一个 Bug 创建后，计划先显示测试中还是开发中？

**问题**：你同时明确未部署新 Bug 可回测试中，以及修复中的任务使计划回开发中；而 Bug 创建会立即使任务进入修复中，发生在同一时刻时按哪条规则显示？

➡️ **建议统一按实际工作聚合**：仍有开发/修复工作未完成时为开发中；代码均已修复、等待人工复测验收时为测试中；全部任务人工验收已完成时为计划已完成。这样“回测试流程”包含必要的修复阶段，而不让两个规则来回覆盖。

**用户答复**：统一按实际工作聚合：还有开发或修复工作未完成→开发中；代码已修复、等待人工验收→测试中；所有任务验收完成→已完成。  
**确认结果**：采用统一优先级，替换未部署新增 Bug 一律直接显示测试中的模糊表述。判断基于实际开发/修复就绪和验收情况，不仅看粗粒度任务标签。  
**状态**：已确认。

### Q051 — 已有 release 修复后，是否形成同版本的新修订？

**问题**：已有 `release/x.x.x` 的计划被 Bug 重新打开，修复验收结束后，是继续维护这条 release 并准备新部署，还是另建新的 release 版本？

➡️ **建议继续使用所属 release 分支，保存新的提交快照、构建和待部署修订，旧 feature 保持只读，旧部署记录保留**。任务再次验收完成时准备新修订，不重复创建同名分支，也不自动创建新计划；运维按新修订重新部署并回报。

**用户答复归纳**：计划初始版本为 release/x.x.0，后续修复创建 release/x.x.1、release/x.x.2 等递进的小修复版本。  
**确认结果**：发布修复使用新的补丁版本分支，未采纳继续更新同一个 release 分支的建议。原计划保留并关联多个发布版本，不因修复自动创建新计划。  
**设计衔接**：Bug 发现版本与修复版本分开记录；补丁继续遵循修复、人工验收、形成完整待发布版本和本地部署回报的流程。  
**待明确**：旧版本 Bug 的新补丁基线，以及用户选择传播目标时的版本粒度，在 Q053 对齐。  
**状态**：编号与新增分支原则已确认。

### Q052 — 本版本任务完成，是否要等所有选中传播目标？

**问题**：当前版本 Bug 已修复并通过测试，但用户选择的某个更高版本仍在处理冲突，源任务和源计划是否可以先完成，还是必须等待全部选中目标修复完成？

➡️ **建议本版本任务按本版本复测结果验收，跨版本传播单独跟踪**。源任务可完成，但传播批次仍显示进行中或部分失败，不能显示所有版本都已修复。这样保持已确认的独立目标继续处理规则；若你要求源任务承担全部选中目标，也可将其全部完成设为验收前置。

**用户答复**：本版本任务按本版本验收，跨版本传播单独跟踪；源任务可以完成，传播仍可进行中或部分失败，不能显示全部版本已修复。  
**确认结果**：源任务/计划完成与传播批次完成解耦。结合 Q051，本版本验收针对源计划本轮补丁修复成果，而不是原地修改已发布旧版本。  
**状态**：已确认。

**用户答复**：基于最新已验收、且所有必要仓库已完整形成的1.2.2。  
**确认结果**：新补丁采用同系列最新已验收且完整形成的版本作工作基线；Bug发现版本独立保留。完整形成与实际已部署不同，基线不只取当前部署版本。  
**设计应用**：传播目标由用户明确选择，审批清单展示基线和拟生成的新补丁；未选择的系列/主分支不自动加入。基线变化须按确定的内容与版本一致性规则处理。  
**状态**：已确认，进入Q021整体共同理解确认。

## 14. 早期识别的设计陷阱（历史）

以下保留Q071之前识别的行为差异，用于追溯。涉及平台代码工作区、分支操作、自动建仓和推送的条目已经失去现行执行前提，不是新的实现任务；新的风险边界是上报是否可信、内部确认如何生效、只读观察能证明什么，见第19节。

1. 提示词描述职责；平台执行 AI 的身份、工具权限和运行状态需要单独管理。
2. AI 写“完成”不等于代码已推送、任务已验收或部署已成功。
3. 分支会变化；批准和测试需要知道当时对应的确切内容版本。
4. 报告有新版本时，原批准不能无条件转移到新版本。
5. 自动 AI 互相回应可能无法收敛，需要预算、轮数与人工接管机制。
6. 六种岗位不能直接等同六个固定流水线状态；真实工作存在并行和退回。
7. 当前产品不执行被管理项目自动化测试，测试图文创建 Bug 不等于平台复现或测试通过；Judex 自身 E2E 要求另行保留。
8. 上传一个网页不等于有了可可靠驱动流程的业务字段。
9. 外部 Git 可自行操作，但 Judex 的来源纳管资格和审批合并规则需要独立执行，不能以外部自由操作为由跳过。
10. 自动建仓、推送、登记和发布有部分成功的可能，应支持查询、恢复和幂等。
11. 人类角色与 AI 工作身份混用，会让用户误认为真人已经发言或批准。
12. 本地工具兼容需要统一协议与能力声明，不能默认所有客户端拥有相同自动化接口。
13. AI 共识、发送确认、中间层推进和结论层全员通过是不同事实，不能用一张同意票完成最终结论。
14. 个人提示词不能悄悄修改整个项目的角色提示词，合成与冲突规则也不能仅凭实现者猜测。
15. 一次 AI 运行结束或流程被取消，不应被统计为接收方已经接受。
16. 不冻结报告和接收集合，就可能在移除反对者或修改内容后错误沿用旧票。
17. 分支自动发现与唯一来源识别不同，需区分平台创建事实、CLI 声明和远端关系推断。
18. 整条低版本 release 合入高版本可能带入无关维护改动；修复传播要识别提交集合与依赖。
19. 已形成的旧release保留历史；新修复发布使用下一补丁分支，部署与Bug证据固定具体版本和提交，不能以移动分支名称代替。
20. 开发中的分支不属于已确认修复传播范围，不能继续自动建同步待办。
21. 平台内部代码若审批前已推候选分支，已经违反先批后推；审批材料应可在平台内部审阅。
22. 开发基线现已由 Q033 明确为计划 feature，不再保留阶段初直接用 release 取代它的方案。
23. AI 判断层级，命中配置节点强制结论层已明确；不能通过提示词降级规则。
24. 首票计时、一票有效反对失效适用于待处理审批；审批结束不显示投票入口，服务端也拒绝旧版本和迟到请求。
25. 任务开发完成不等于人工验收已完成；全部任务已完成才聚合计划已完成，不再加一次额外手工计划测试完成。
26. 初版在当前批准范围内仍须完成验收；Q065已允许维护按确认批次独立发布，不能用范围外未关闭Bug阻塞该批。开发完成不替代测试，非缺陷等处置也不等于修复成功。
27. 新Bug使工作回退，部署历史独立保留；工作状态和部署状态已确认分开显示。
28. Bug绑定版本和任务，不自动进入新计划池；AI只能处理用户选中传播目标，不默认同步全部高版本或主分支。
29. 界面创建Bug必须完成任务关联，不能让无归属素材随意将任务置为修复中。
30. Bug复测和任务验收分别留证，不能以代码合入或AI推断代替人工确认；测试或经理手工验收的动作应明确记录。
31. 源任务验收和传播完成独立；源任务完成不能把其他目标的进行中或失败覆盖为成功。
32. 修复发布需要新补丁版本分支，不能原地改旧release再仅新增一条部署记录。
33. Bug发现版本、工作基线、修复发布版本和实际部署版本分别保存，不互相覆盖。
