# AI工作空间、会话历史与执行环境

更新时间：2026-09-24。用户已确定平台项目资料、SQLite会话历史和OpenSandbox执行；Q084确认业务会话随岗位交接，正式议题/报告/可共享依据向团队开放，前任个人提示词及私人配置不因交接自动暴露。本文目录与部署方式仍为工程建议，不因Q084答复一并成为已批准实现。

本轮只更新设计，不创建数据库、沙箱、PVC或运行服务。SQLite仅被指定用于会话历史，不能据此将全部业务数据存储也定为SQLite。

## 1. 用户提出的结构与保留原则

```text
project/
  plan/
    repos/
      repo1/
      repo2/
    resources/
      robot1/
      robot2/
    talks/
      robot1/
      robot2/
```

该结构可用于按计划组织AI上下文：代码、资料和会话入口分开；上传内容绑定稳定机器人，接任者接续业务，不随前任账号消失。这里的robot1必须是项目内同一个稳定机器人，不能在每个计划中重新创建一个互不关联的身份。

需要补充的主要场景：

- 计划尚未建立时，项目提案、初始讨论和上传材料已有存放需求，不能强制先造一个计划。
- 岗位经验要跨计划积累，不能随某个计划归档而从机器人上下文中消失。
- 多个机器人参与同一议题，需要引用一份共同讨论和正式报告，不能各自复制一份后独立改写。
- 同一仓库在不同计划或任务下可能对应不同分支；并行分析不能共用一个不停切分支的可变目录。

## 2. 推荐的逻辑目录

```text
projects/<project-id>/
  resources/                         # 尚未归入计划或跨计划的项目资料
    shared/
    robots/<robot-id>/
  robots/<robot-id>/
    knowledge/                       # 跨计划的岗位经验和工作要求
  discussions/<discussion-id>/        # 一份共同议题、正式报告及版本引用
  plans/<plan-id>/
    repos/<repo-id>/<snapshot-id>/    # 本计划关联代码的只读视图
    resources/
      shared/
      robots/<robot-id>/              # 本计划内与机器人关联的报告和成果
    tasks/<task-id>/                  # 任务目标、关联分支和材料的上下文视图
    talks/<robot-id>/<session-id>/    # 授权的摘要/导出，不是另一份可独立修改的历史
```

这是业务组织和AI可读视图，不要求每一处引用都复制一份物理文件。具体名称、分层深度和文件存储产品属于工程选择；主体继续沿用用户的plan/repos/resources/talks。

项目、计划、任务、机器人、议题、会话和产物使用稳定标识，显示名称可以修改。文件归属和引用依据这些标识保存，不能只靠文件名或路径猜测。资料从提案进入计划时可以新增关联，不必为了迁移目录复制内容并丢掉旧引用。

### 2.1 资源归属与继承

resources/robots表示材料与该机器人的业务关系，不自动表示仅该机器人可读。共同项目事实继续按既有权限共享；拥有者、来源、关联对象和可见范围分别记录。

每个上传文件保留原始版本、来源真人/机器人、所述工作时间与平台接收时间。订正产生新版本并指向原记录，避免相同文件名和不同时间材料相互覆盖。AI可以生成摘要或分析，但不能覆盖原报告来伪装源信息。

岗位知识放在项目级robots/knowledge；计划级资料保留原上下文。换人时继承岗位责任、知识和相关业务材料，历史作者不改写；个人表达偏好、个人提示词原文和私人凭据仍遵守原有可见范围，不自动进入交接导出。

### 2.2 仓库视图

repos是只读分析输入，必须能定位仓库、关联分支和本次实际读到的提交。Q085明确用户侧分支自由，计划/任务/Bug修复分别关联，不限制名称、父分支、创建来源或合并方式。任务可引用多个仓库分支，同一分支可被多个对象引用；共享代码按各任务目标分别分析，不能把分支整体进度复制给所有任务。

建议平台的只读接入服务准备代码快照；每轮分析固定一个输入清单。底层仓库缓存可以复用，但并行运行各自读取确定的快照，不能共享一个会被checkout到不同分支的工作目录。新提交到达后产生新的观察/分析依据，旧运行结果仍指向旧快照。

平台更新自己的只读缓存属于获取分析材料，不代表获准修改客户代码。没有同步到可读仓库的本地变更仍不可见；读取失败和最后分析时间要如实展示。

## 3. 会话与共同议题

推荐区分三个对象：

| 对象 | 含义 |
| --- | --- |
| Discussion共同议题 | 围绕一个业务问题的共同发言、正式报告和版本关联；可涉及多计划或在计划建立前存在 |
| RobotSession机器人工作会话 | 某机器人为阅读资料、分析和整理结论而开展的会话，可引用共同议题和材料 |
| AgentRun一次运行 | 在特定提示词版本和输入清单下的一次执行，记录开始/结束、可见工具动作、输出、消耗和失败 |

SQLite保存会话主记录。talks目录保存授权的可读摘要、导出和附件引用；这些可以重新生成，不能与SQLite分别接受修改、各自成为真实历史。正式讨论按议题保存一份，按机器人查看参与记录即可。

只保存可见消息、工具结果、业务输出和运行元数据，不要求模型隐藏推理。原始模型请求若包含个人配置，不应直接进入全项目可读的会话导出；引用受限配置版本即可保留追溯。

Q084已确认：业务会话随稳定岗位交接；正式议题、报告及可共享依据向团队开放；前任个人提示词与私人配置不因交接自动暴露。其他原始工作会话沿用既有职责和内容权限，不能仅凭talks/robot目录名扩大公开范围。此前“默认仅当前任职者和负责人”的表述属于推荐方案，不冒充用户逐字确定的排他访问清单。

交接导出和会话读取应按内容区分：可继承的业务上下文、可向团队共享的正式材料、保留原权限的个人配置。过滤个人配置不改写历史操作者，也不把应共享的正式事实变成机器人私有数据。

## 4. SQLite的适用方式

**已确定**：会话历史使用SQLite。**建议部署方式**：由Judex服务持有数据库，机器人通过受权限控制的接口读取上下文、追加消息和运行结果；不要让多个OpenSandbox直接挂载并修改同一个数据库文件。

SQLite官方说明，WAL模式允许读写并行，但同一数据库同时只有一个写入者，普通WAL依赖同机共享机制，不能用于跨主机网络文件系统。来源：[SQLite WAL](https://www.sqlite.org/wal.html)。

据此，建议每个数据库明确负责的服务实例，在可靠支持锁与同步的持久存储上使用短事务；模型推理不占用数据库事务。是否按项目分库可按规模选择，不能把“每个机器人一个目录”机械等同为“必须每机器人一个SQLite”。PVC本身也不证明底层适合SQLite，需要验证实际文件系统。

会话记录与项目/计划/机器人/议题/运行标识关联。API调用方可以并发，数据库由服务协调写入。需要多节点部署时，调用方走服务路由，不让不同节点直接共同打开网络共享上的数据库文件。其他业务数据的存储方案不由本次会话历史选型替代。

备份或向沙箱提供只读副本时，由服务生成一致快照，避免直接复制正在写入的数据库文件。官方提供在线Backup API和VACUUM INTO等方式。来源：[SQLite备份](https://www.sqlite.org/backup.html)。

实现时锁定已修复官方WAL-reset问题的SQLite版本并核验实际驱动版本；当前官方文档列出3.51.3及以后与相应旧系列回移版本。该事项属于工程版本管理，不要求用户重新选择数据库。

## 5. OpenSandbox运行视图

**已确定**：平台AI在OpenSandbox中执行。这里承载Agent运行和获准的工具处理；不意味着把模型本体部署进每个沙箱，模型服务仍按项目配置调用。

持久工作资料与一次沙箱的生命周期分开。建议每次运行只获得本次获准的输入和独立写目录：

```text
/workspace/
  project/        # RO：本次可读项目资料与岗位知识
  plan/           # RO：本次计划/任务上下文
  repos/          # RO：本次关联代码快照
  talks/          # RO：按权限取得的会话片段/摘要
  output/         # RW：本次新生成的分析、报告等产物
  scratch/        # RW：可清理的临时文件
```

SQLite主库不挂载给模型。可通过会话API获取上下文，必要时提供过滤后的只读快照。不同运行的output/scratch分开；平台登记产物及来源后，再按既有权限与版本规则归入对应resources/knowledge，不因写出文件自动视为已批准结论。

OpenSandbox官方规范提供卷挂载和readOnly属性，应显式开启只读；Kubernetes示例区分已有PVC、持久PVC和随沙箱清理的临时PVC。项目资料与会话数据不能放在随本次运行删除的卷里。跨节点挂载与共享取决于实际存储后端，不由支持PVC这一事实自动保证。来源：[Lifecycle规范](https://github.com/opensandbox-group/OpenSandbox/blob/main/specs/sandbox-lifecycle.yml)、[PVC示例](https://github.com/opensandbox-group/OpenSandbox/blob/main/docs/examples/kubernetes-pvc-volume-mount.md)。

当前官方main文档还说明Pool模式需要在模板预挂载，不能在创建沙箱时同时指定poolRef和动态volumes。部署时固定OpenSandbox版本，实际验证挂载与生命周期，不用main文档替代目标环境验收。

## 6. 执行权限与状态边界

OpenSandbox提供运行隔离，不决定业务授权。Q071继续有效：AI可以读取、检索、解析资料并生成办公分析；不恢复客户项目开发、构建测试、Git写入、部署或升级执行。

只读仓库/资料与受限写目录、工具权限、出站权限需要分别落实。不能因目录只读就认为网络请求也受限；沙箱不持有客户Git写凭据或生产部署凭据。具体网络方案在选定部署版本和运行后端时验证，本轮未实施任何网络配置。

业务状态仍通过平台接口按职责和已确认规则修改。SQLite消息写入和output报告生成不是投票，也不是完成验收。Q081明确开发完成后待测试，测试通过后最终完成；Q082明确AI推断只更新进度和疑点，不直接撤销人工完成，正式Bug或明确退回按规则联动。

## 7. 验证计划与当前状态

后续实现至少验证：

1. 计划建立前可保存材料和开展讨论；跨计划岗位知识可持续引用。
2. 换人保留机器人业务资料和会话关系，历史真人不改写，个人配置按原权限处理。
3. 同一议题只有一个共同版本，各机器人视图和会话均引用它。
4. 并行计划/运行读取各自明确的代码和材料快照，不能彼此切换或覆盖。
5. 沙箱结束后持久资料和会话仍可读取，临时输出不会冒充已归档成果。
6. SQLite服务并发写入、重试、重启和一致备份恢复；沙箱无法直接改写历史库。
7. 只读代码与资料不可被运行修改；分析产物能在获准写区生成并正确登记。
8. 运行失败不伪造分析完成或人工决定；新旧成果、角色配置和来源时间可追溯。

本文所述后端架构尚未实施，未安装/启动OpenSandbox或创建SQLite库。后续Q021确认后的Demo已提供浏览器逻辑目录、资料上传和自由分支关联，但不能证明本篇的持久存储、沙箱或会话服务已经落地；本轮实测范围见Demo说明。
